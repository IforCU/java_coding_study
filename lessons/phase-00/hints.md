# Phase 0 — 단계별 힌트

한 번에 모든 힌트를 적용하기보다 현재 실패한 단계부터 확인하세요. 완성 SQL과 해설은 이 문서에 포함하지 않습니다.

## 힌트 1: 실행 환경부터 확인

`docker version`은 클라이언트와 서버 정보를 구분합니다. 클라이언트 정보만 보이고 서버 연결이 실패하면 Docker 엔진이 준비되지 않은 상태입니다. 애플리케이션 코드를 고치기 전에 Docker Desktop과 Linux 컨테이너 엔진 실행 여부를 확인합니다.

`docker compose version`과 `docker compose --profile phase0 config --quiet`도 확인합니다. 설정 검사에 성공한 것과 실제 컨테이너가 실행된 것은 다릅니다.

## 힌트 2: 상태를 서비스별로 확인

`docker compose --profile phase0 ps -a`로 DB, 마이그레이션, 웹 서비스를 각각 봅니다. 마이그레이션은 할 일을 마친 뒤 성공 코드로 종료하는 서비스이므로 계속 실행 중이어야 하는 웹 서버와 판정 기준이 다릅니다.

필요한 서비스의 로그만 조회합니다.

```sh
docker compose --profile phase0 logs --tail 80 db migrate legacy
```

자격 증명이 들어 있는 설정 전체를 채팅이나 공개 게시물에 붙여 넣지 않습니다.

## 힌트 3: 포트와 주소를 구분

8080이나 5432가 이미 사용 중이면 루트 `.env`에서 호스트 공개 포트를 바꾸고 재실행합니다. `.env.example`을 참고하고 실제 운영 자격 증명은 사용하지 않습니다.

컨테이너 내부의 DB 호스트는 서비스 이름입니다. 호스트에서 접속하는 `127.0.0.1`과 같은 주소로 생각하지 않습니다. `.env`의 포트를 바꾸었다면 브라우저 확인 주소도 바뀝니다.

## 힌트 4: live와 ready를 나누어 생각

Hello World와 live가 성공하는데 ready만 실패한다면 DB 접속, 마이그레이션, 메타데이터를 순서대로 확인합니다. HTTP 연결 자체가 실패한다면 Tomcat 실행과 포트 매핑부터 확인합니다.

이 구분은 실패 범위를 좁히기 위한 것입니다. 로그에서 내부 오류를 발견하더라도 이를 응답 본문으로 반환하도록 코드를 바꾸지 않습니다.

## 힌트 5: SQL의 세 부분

조회문은 반환할 열, 조회할 테이블, 대상 행의 조건으로 나누어 생각합니다. 문제의 열 순서와 환경 조건을 각각 표시해 보세요. PostgreSQL의 스키마와 테이블은 점으로 구분하며, 문자열 값과 식별자는 다른 개념입니다.

전체 열을 반환하면 검증에 필요한 열 수와 순서를 보장하기 어렵습니다. 문제에서 요청한 두 열만 선택하세요. 문법은 [PostgreSQL 17 SELECT 공식 문서](https://www.postgresql.org/docs/17/sql-select.html)를 참고합니다.

## 힌트 6: 실습 실패와 실행 실패를 구분

기본 화면과 ready가 정상인데 실습 스크립트만 실패하면 starter SQL의 문법, 두 열의 순서, 행 개수를 확인합니다. 미완성 TODO가 기본 실행에 영향을 주면 실습 격리가 깨진 것이므로 기본 빌드 경로를 먼저 점검합니다.

검증값을 SQL에 직접 써서 통과시키는 것은 과제 목적에 맞지 않습니다. 데이터가 변경되어도 테이블의 현재 값을 읽는지 확인하세요.
