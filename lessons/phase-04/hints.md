# Phase 4 — 단계별 힌트

## 1. 입력 오류 먼저 분리

두 값 중 null이 있거나 값이 같으면 정렬 대상 두 계좌가 아닙니다. 같은 값을 가진 서로 다른 UUID 인스턴스도 생각해 보세요. 오류 종류는 과제에서 요구한 `IllegalArgumentException`입니다.

## 2. 기준을 한 가지로 고정

A→B와 B→A는 이체 방향은 다르지만 잠금 대상 집합은 같습니다. 순서는 요청 방향이 아니라 두 식별자의 비교 기준으로 결정되어야 합니다.

## 3. Java와 DB 비교 방식 확인

Java의 long은 부호가 있습니다. DB가 UUID를 비교하는 바이트 순서와 Java의 기본 비교 구현이 같은 방식인지 확인하세요. 특히 최상위 비트가 바뀌는 고정 테스트의 기대 순서를 먼저 손으로 적어 보세요.

UUID의 정규 문자열은 길이와 하이픈 위치가 고정됩니다. 바이트 표현과 정규 문자열 표현에서 순서가 어떻게 이어지는지 살펴보되, 대소문자와 비정규 입력 문자열을 그대로 비교하는 정책과 혼동하지 않습니다.

## 4. 결과를 변경할 수 없게 하기

정렬이 맞아도 반환 목록을 호출자가 바꿀 수 있으면 계약을 지키지 못합니다. Java 컬렉션 API에서 수정할 수 없는 결과를 만드는 방법을 확인하세요. 원본 UUID는 불변 값입니다.

## 5. 테스트가 검증하는 범위

이 정책 테스트는 잠금 순서를 계산할 뿐 PostgreSQL 연결을 열지 않습니다. 실제 동시 요청, 대기, timeout, rollback은 실제 DB 통합 테스트에서 확인합니다. 단위 테스트 통과를 deadlock 부재의 증명으로 기록하지 않습니다.

## 6. 실패 후 네 가지 상태 확인

이체가 실패했을 때 계좌 잔액만 보지 않습니다. 요청 예약, 출금·입금 원장, 일일 사용액이 이전 상태와 같은지도 확인합니다. 예외를 잡아 성공처럼 반환하면 트랜잭션 경계에서 어떤 일이 일어날지 생각해 보세요.
