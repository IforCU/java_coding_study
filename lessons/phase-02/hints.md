# Phase 2 — 단계별 힌트

계좌 화면 작성 TODO의 힌트는 [JSTL 실습 힌트](jstl/hints.md)에 따로 있습니다.

## 1. 네트워크 탭부터 관찰

GET 화면이 보인 뒤 폼을 제출해 요청 두 개를 비교합니다. 첫 요청의 POST 본문과 응답의 `Location`, 이어지는 GET URL을 확인합니다. redirect 후 request attribute가 유지될 것이라고 가정하지 않습니다.

## 2. 세션과 요청의 범위

request attribute는 한 요청을 처리하는 동안 사용합니다. session attribute는 같은 브라우저 세션의 여러 요청에서 읽습니다. 선택 고객과 CSRF 토큰을 각각 어떤 범위에 저장했는지 Servlet에서 찾습니다.

CSRF 오류가 나면 새로 GET으로 폼을 열어 세션과 토큰을 받은 뒤 같은 세션으로 제출했는지 확인합니다. 정상 검증을 위해 토큰 검사를 제거하지 않습니다.

## 3. 문자열 정리 순서

입력이 null인 상태에서 문자열 메서드를 부르면 과제에서 요구한 예외가 아닌 예외가 발생할 수 있습니다. 또 정리 전 길이와 정리 후 길이는 다릅니다. 80자 이름 앞뒤에 공백이 있는 테스트가 어떤 순서를 요구하는지 생각해 보세요.

`String` API의 공백 제거 메서드마다 다루는 문자 범위가 다릅니다. ASCII 공백만 있는 경우와 `\u2003` 같은 Java 공백을 각각 확인하세요. 내부 공백을 지우거나 이름을 모두 소문자로 바꿀 필요는 없습니다.

## 4. DAO에서 자원 경계 찾기

Connection, PreparedStatement, ResultSet이 각각 어디에서 생성되고 닫히는지 중괄호 범위를 그려 보세요. 오류가 발생해도 동일한 정리가 적용되는지 확인합니다. 풀에서 빌린 연결은 정리가 빠지면 다음 요청에 영향을 줍니다.

## 5. 서로 다른 보호 경계

서버 입력 검증, PreparedStatement 바인딩, JSP 출력 이스케이프는 적용하는 위치가 다릅니다. 이름 길이가 유효하다는 이유로 나머지 처리를 생략할 수 있는지 정상 소스를 통해 확인합니다.

## 6. 실행 결과 분류

단위 테스트는 DB 없이 서비스 검증과 HTTP 분기를 확인할 수 있습니다. 실제 PostgreSQL 조회와 Tomcat JSP 렌더링은 Docker/DB 실행 후 별도로 확인해야 합니다. 실패한 실습 TODO를 정상 WAR 실패와 혼동하지 않습니다.
