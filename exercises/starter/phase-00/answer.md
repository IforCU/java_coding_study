# 과제 1 : 요청과 실행 구조 기록 

1. 브라우저가 호출하는 주소와 Java 컨테이너가 DB에 연결하는 주소는 어떻게 다른가요?

    > 브라우저가 호출하는 주소는 tomcat을 통해 서빙되고 있는 index.jsp 입니다. Java 컨테이너가 호출하고 있는 것은 DB로 서버가 띄워져 있는 주소에 JDBC를 통해 연결하여 DB 데이터를 가져오는것이고, 이를 통해 다시 사용자에게 전달되는 구조입니다. 

    **보충 해설:** 흐름은 맞습니다. 다만 질문의 핵심은 파일 이름보다 **접속 주소와 프로토콜의 차이**입니다. 브라우저는 기본 설정에서 `http://127.0.0.1:8080/`으로 HTTP 요청을 보내고, Tomcat이 `index.jsp`를 처리해 HTML을 반환합니다. Java 컨테이너는 `jdbc:postgresql://db:5432/bank_learning`으로 연결합니다. 여기서 `db`는 Compose 내부 서비스 이름이며, 호스트에서 사용하는 `127.0.0.1`과 다릅니다. 실제 DB 이름과 공개 포트는 환경 설정에 따라 달라질 수 있습니다. 또한 이 Phase의 `/`는 DB를 조회하지 않으며, `/health/ready`가 JDBC로 메타데이터를 조회합니다.

2. `GET /`의 JSP와 `GET /health/ready`의 Servlet은 각각 어떤 역할을 맡나요?

    > 기본적인 GET / 은 index.jsp를 호출하는 역할 이고, GET /health/ready는 헬스체크 요청을 2초안에 응답이 날라오면 서버가 살아있다고 판단되는 역할을 맡습니다.

    **정정 해설:** `/`가 JSP를 통해 Hello World HTML을 반환한다는 설명은 맞습니다. `/health/ready`는 단순히 2초 안에 응답하는지 보는 기능이 아니라, **애플리케이션이 JDBC로 DB에 연결하고 필요한 메타데이터까지 읽을 수 있는지** 확인합니다. `DatabaseProbe`가 환경 `local-learning`의 스키마 버전이 `1`인지 검사하고, `BootstrapServlet`이 성공 시 HTTP 200과 JSON, DB 연결·조회 실패나 메타데이터 불일치 시 HTTP 503과 JSON을 반환합니다. DB 조회 없이 Servlet 응답 가능 상태를 확인하는 경로는 `/health/live`입니다.

    **시간 설정 보충:** `HealthCheck.java`의 2초는 점검용 HTTP 클라이언트가 Tomcat에 연결할 때의 제한이고, 8초는 HTTP 요청 타임아웃입니다. Servlet 자체의 ready 판정 조건과는 구분해야 합니다. DB 연결·소켓·쿼리에 적용하는 제한은 `DB_TIMEOUT_SECONDS` 설정이며 코드의 기본값은 3초입니다. 이 제한들을 더해 전체 응답 시간이 고정된다고 해석하면 안 됩니다.

3. DB health check가 성공했는데 ready 요청이 실패할 수 있는 이유는 무엇인가요?

    > DB의 타임아웃은 2초로 되어 있지만, 브라우저에게 해당 응답이 날라가는데는 8초가 걸림 DB는 정상적인 연결되었지만, 브라우저 응답시간 초과로 발생할 수 잇음 

    **정정 해설:** DB 2초와 브라우저 8초라는 설명은 서로 다른 설정을 혼동한 것입니다. 2초와 8초는 위 `HealthCheck`의 HTTP 클라이언트 설정이며, 브라우저가 반드시 8초 동안 기다리거나 응답에 8초가 걸린다는 뜻이 아닙니다. 이 질문의 핵심은 **DB 서버가 접속을 받을 수 있는 상태와 애플리케이션이 필요한 데이터를 사용할 수 있는 상태의 차이**입니다.

    Compose의 DB health check는 DB 컨테이너 내부에서 `pg_isready`로 PostgreSQL의 접속 수락 상태를 검사합니다. 이것만으로 Java 컨테이너의 JDBC 인증·네트워크 연결이나 테이블·초기 데이터 준비까지 확인하지는 않습니다. 따라서 DB는 healthy여도 Java 측 연결 설정이 잘못되었거나, `bootstrap.app_metadata`가 없거나, 필요한 행이 없거나 스키마 버전이 다르면 ready가 실패할 수 있습니다. 정상 시작에서는 `migrate` 성공 후 WAR를 실행하도록 의존성을 두지만, 실행 후의 상태는 ready로 별도 확인합니다.

4. DB 데이터가 저장되는 볼륨과 WAR가 실행되는 컨테이너는 어떤 관계인가요?

    > 현재로써는 docker를 기반으로 같이 묶여있는 관계이며, 때에 따라서 서버가 분리되어 있는경우도 있음 다만 지금은 컨테이너로 분리되어 있음

    **정정 해설:** DB 컨테이너와 웹 컨테이너가 분리되어 있다는 관찰은 맞습니다. 여기에 **데이터의 수명과 앱 실행의 수명이 분리된다**는 설명이 필요합니다. `postgres_data`라는 이름 있는 볼륨이 DB 컨테이너의 `/var/lib/postgresql/data`에 연결되어 PostgreSQL 데이터를 보관합니다. WAR는 `legacy` 컨테이너의 Tomcat에서 실행되며 이 DB 볼륨을 직접 읽지 않고 JDBC로 DB 서버에 접근합니다.

    일반 `docker compose down` 후 다시 `up`하면 컨테이너는 재생성되어도 볼륨에 있던 데이터는 유지됩니다. 웹 컨테이너를 재빌드·교체하는 것과 DB 데이터를 보존하는 것은 별개입니다. 볼륨 삭제 옵션을 사용하면 보존 조건이 깨지므로 이 실습에서는 사용하지 않습니다. DB 볼륨은 컨테이너 교체 시 영속성을 제공하지만 별도의 백업을 대신하지는 않습니다.

5. Java 17 선택과 `jakarta.servlet` 선택은 왜 따로 확인해야 하나요?

    > 자바17은 언어의 문법 선택이고, jakarta.servlet은 http요청과 응답을 실질적으로 이루는 요소라 지원하는 자바 언어가 정해져 있음 

    **정정 해설:** Java 17 선택은 문법뿐 아니라 **컴파일 대상과 실행할 JVM·표준 라이브러리의 기준**을 정하는 것입니다. `jakarta.servlet` 선택은 웹 요청·응답을 다루는 **Servlet API의 패키지와 규격**을 정하는 것입니다. 따라서 Java 실행 환경이 맞는지와, 코드가 사용하는 Servlet API를 Tomcat이 제공하는지는 각각 확인해야 합니다. Java 17을 사용한다고 Servlet API의 버전이나 패키지가 자동으로 결정되지는 않습니다.

    이 저장소의 Phase 0은 루트 POM에서 Java 컴파일 기준을 17로 지정하고, 모듈 POM에서 `jakarta.servlet-api:6.0.0`을 `provided`로 선언하며, Dockerfile에서 Tomcat 10.1의 JDK 17 이미지를 사용합니다. `provided`는 컴파일에 필요한 API를 사용하되 실행 시에는 Tomcat이 제공하도록 WAR에 해당 API 의존성을 넣지 않는 설정입니다. 그래서 코드의 API와 실행 컨테이너의 API가 맞아야 합니다. `javax.servlet`과 `jakarta.servlet`은 패키지 이름이 다르므로 단순히 JDK만 바꾸어 같은 것으로 취급할 수 없습니다.
