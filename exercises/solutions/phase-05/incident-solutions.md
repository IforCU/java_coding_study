# Phase 5 장애 분석 해설

이 문서는 과제를 시도한 뒤 비교하는 정답 자료입니다. 격리 랩의 PASS는 증상 재현 성공이며, 아래 교정 방향을 정상 서비스에 새 오류 기능으로 추가하지 않습니다.

## 1. 잘못된 SQL 조건

소유자 조건이 빠지거나 논리 연산자 범위가 잘못되면 다른 소유자의 행이 섞입니다. 조회 대상 식별자와 접근 가능한 소유자 범위를 함께 바인딩해 제한하고, OR/AND 조건의 괄호를 검토합니다. 입력 검증만으로 누락된 행 조건이 보완되지는 않습니다.

정상·타 소유자·없는 대상·조건 경계의 반환 ID 집합을 검증합니다. 실제 DB 랩은 자기 fixture ID 범위만 조회하여 사용자 데이터를 읽지 않습니다.

## 2. 연결 풀 고갈

빌린 연결을 반환하지 않으면 사용할 수 있는 풀이 줄어듭니다. Connection·Statement·ResultSet은 try-with-resources로 예외와 조기 반환에서도 정리하고, 전체 풀의 종료는 애플리케이션 생명주기가 소유합니다. 느린 외부 작업 동안 DB 연결을 오래 잡는 범위도 줄입니다.

풀을 늘리는 일만으로 누수를 고치지 않습니다. 성공·실패 반복 후 대여 가능 수와 대기·timeout·회복을 확인합니다.

## 3. 느린 쿼리

작업량과 대기 시간의 한계가 없으면 한 요청이 자원을 오래 점유할 수 있습니다. 조건과 인덱스, 정렬·반환량, 실행 계획과 잠금 대기를 나누어 조사하고 적절한 DB/JDBC timeout을 설정합니다. 취소 예외는 내부 SQL과 입력을 노출하지 않는 오류로 변환하며 연결도 정리합니다.

`pg_sleep` 랩은 취소 경로와 SQLSTATE `57014`를 검증합니다. 실제 업무 SQL 최적화는 실행 계획과 대표 데이터 분포를 별도로 측정해야 합니다.

## 4. 잘못된 트랜잭션 범위

auto-commit이나 분리된 트랜잭션이 출금을 먼저 commit하면 입금 전 실패를 되돌릴 수 없습니다. 잔액·원장·중복 요청·한도 사용을 같은 DataSource와 서비스 트랜잭션 경계에 둡니다. 예외를 삼키거나 독립 트랜잭션에서 원장만 commit하지 않습니다.

출금 후 오류를 주입하고 관련 상태 전체가 이전 값으로 복구되는지 실제 PostgreSQL에서 확인합니다. Spring 프록시를 거치지 않은 서비스 생성 테스트만으로 rollback을 증명하지 않습니다.

## 5. 권한 검증 누락

인증된 사용자라는 사실과 대상 계좌를 볼 수 있다는 권한은 다릅니다. 서버가 principal을 기준으로 소유권·역할을 확인하고, 사용자 입력의 소유자 ID를 신뢰해 범위를 넓히지 않습니다. UI 버튼 표시와 별개로 서버 요청을 거절해야 합니다.

본인·타 소유자·관리자·미인증 사용자별 접근 행렬과 거절 후 부작용 부재를 검증합니다. 관리 기능의 역할 검사도 동일한 원칙을 따릅니다.

## 6. 중복 거래

단순 재실행은 같은 출금을 반복합니다. 고유 requestId와 요청 내용을 저장해 같은 ID·같은 내용은 기존 결과로 수렴시키고, 같은 ID·다른 내용은 충돌로 거절합니다. 요청 예약과 잔액·원장·한도를 한 트랜잭션에 둬야 부분 상태를 피할 수 있습니다.

동일·동시 재요청과 commit 후 응답 유실을 실제 DB에서 검증합니다. 잔액뿐 아니라 원장 건수와 한도 사용을 함께 확인합니다.

## 7. 세션 만료

principal이 저장되어 있다는 이유만으로 만료 후에도 반환하면 재인증 경계가 사라집니다. 현재 시각과 만료 시각을 일관되게 비교하고 만료 상태를 복원하지 않도록 합니다. 시간 의존 로직은 고정 Clock으로 경계를 검증합니다.

정상 Spring Security 환경에서는 세션 만료·로그아웃·로그인 시 ID 변경을 따로 확인합니다. HTTP Basic 자격 증명을 매 요청에 보내면 세션이 없어도 다시 인증될 수 있으므로 세션 검증에서는 그 헤더를 제거합니다.

## 8. 잘못된 데이터 매핑

같은 타입의 인자 순서가 바뀌면 컴파일은 성공하면서 잘못된 화면 값이 생길 수 있습니다. 열 별칭과 명시적 매핑을 고정하고 생성자 순서·UUID·금액·시각 타입을 확인합니다. 금액을 부동소수점으로 읽지 않습니다.

각 필드에 서로 다른 sentinel 값을 주고 필드별로 단정합니다. 성공 조회 건수만 확인하는 테스트로는 잘못된 매핑을 발견하기 어렵습니다.
