# 학습 프로젝트의 금액 처리 기준

현재 계좌 시뮬레이터는 원화 한 통화와 1원 단위를 사용합니다. 실제 금융 상품의 이자·세금·환율 계산 규칙은 포함하지 않습니다. 금액 표현의 정확성과 업무 정책을 구분해 학습하는 기준입니다.

## BigDecimal 사용

입력은 `new BigDecimal("1000")`처럼 문자열에서 생성합니다. `new BigDecimal(0.1)`은 이미 이진 부동소수점으로 표현된 값을 전달하므로 의도한 십진수와 차이가 생길 수 있습니다. 계산 도중에도 `double`, `float`로 바꾸지 않습니다. [Java 17 BigDecimal 공식 문서](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigDecimal.html)

`BigDecimal`은 불변이므로 연산 결과를 새 값으로 받아야 합니다. 숫자의 크기와 소수부 표현 scale도 구분합니다. `100`과 `100.00`은 수치가 같지만 `equals()`는 scale까지 비교합니다. 업무상 금액의 대소와 수치 동등성은 `compareTo()`로 판단합니다. [BigDecimal의 비교 규칙](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigDecimal.html#compareTo(java.math.BigDecimal))

## 원 단위 정책

| 입력 | 입출금액 허용 여부 | 이유 |
| --- | --- | --- |
| `100` | 허용 | 양수 원 단위 |
| `100.00` | 허용 | 수치상 100원과 같음 |
| `1E+3` | 허용 | 1000원과 같음 |
| `100.1` | 거절 | 원 미만 금액 |
| `0` | 거절 | 0원 거래는 생성하지 않음 |
| 음수, null | 거절 | 유효한 입출금액이 아님 |

새 계좌의 잔액은 0원일 수 있지만 입출금액은 양수여야 합니다. 입력을 반올림하여 유효한 금액으로 바꾸지 않습니다. 실제 업무에서 반올림이 필요하면 계산 시점, 자리 수, 모드, 차액 처리 기준을 먼저 정해야 합니다.

## 잔액과 거래 기록

입금·출금 성공 시 잔액과 거래 기록이 함께 바뀌어야 합니다. 검증 실패 시 둘 다 보존되어야 합니다. 잔액만 맞는다고 업무 처리가 정확한 것은 아닙니다. 원금과 출금액이 같으면 잔액 0으로 출금할 수 있으며, 잔액 부족은 음수 잔액을 만든 뒤 처리하지 않고 사전에 거절합니다.

이 기준은 Phase 1 메모리 모델의 정책입니다. 단일 DB 트랜잭션, 동시 출금, 멱등성, 외부 기관 대사 검증은 후속 단계에서 별도로 수행합니다.
